FutureMe AI · Technical & Product Brief

FutureMe AI Infrastructureสรุปสำหรับทีม

ระบบไม่ได้ให้ AI ทายว่าเด็ก “ควรเป็นอะไร” แต่ช่วยเก็บหลักฐานจากตัวนักเรียน เชื่อมหลักฐานนั้นกับข้อมูลอาชีพและหลักสูตรที่ตรวจสอบได้ แล้วเสนอหลายเส้นทางพร้อมเหตุผล ข้อจำกัด และแหล่งอ้างอิง

แกนของระบบ สนทนาและสร้าง Profile → ค้นหลักฐานด้วย RAG → ให้คะแนนแบบอธิบายได้ → ตอบอย่างปลอดภัย

Executive Summary

สี่เรื่องที่ทุกคนในทีมต้องเข้าใจตรงกัน

FutureMe ไม่ใช่โมเดลก้อนเดียว แต่เป็นระบบหลายส่วนที่แบ่งหน้าที่กันชัดเจน ถ้าส่วนใดส่วนหนึ่งรับผิดชอบมากเกินไป คำแนะนำจะตรวจสอบยากและเสี่ยงชี้นำเด็ก

1

Base LLM เป็นตัวสนทนา ไม่ใช่ฐานข้อมูล

ใช้คุยกับนักเรียน สกัดข้อมูลเป็นโครงสร้าง และเรียบเรียงคำอธิบาย แต่ไม่ควรใช้จำเกณฑ์รับสมัครหรือคิดคะแนนความเหมาะสมเอง

2

RAG มีหน้าที่ค้นหลักฐาน

ค้นข้อมูลอาชีพ หลักสูตร เกณฑ์รับสมัคร และแหล่งอ้างอิงที่เกี่ยวข้องกับ Learner Profile โดยต้องกรองปี จังหวัด ระดับวุฒิ และสถานะข้อมูลก่อน

3

Recommendation Engine เป็นคนให้คะแนน

คำนวณจากกติกาที่ทีมกำหนด แยกคะแนนความสนใจ ทักษะ บริบทงาน ข้อจำกัด และความพร้อมทางการศึกษา เพื่อย้อนตรวจเหตุผลได้

4

LoRA เป็นงานหลัง validation

ใช้เมื่อมีตัวอย่างบทสนทนาคุณภาพสูงและพบว่า prompt ยังไม่พอ ไม่ใช้สอนข้อเท็จจริงที่เปลี่ยนตามปี และไม่ใช่ตัวกรองคำตอบชั้นสุดท้าย

ประโยคเดียวสำหรับเล่าให้คนอื่นฟัง: FutureMe คุยกับนักเรียนเพื่อสร้าง Learner Profile จากข้อมูลที่เด็กยืนยัน เชื่อม Profile เข้ากับหลักสูตรและอาชีพผ่าน RAG แล้วเสนอหลายเส้นทางด้วยคะแนน เหตุผล และหลักฐานที่ตรวจสอบได้

System Architecture

ภาพรวมระบบที่สั้นที่สุดและยังถูกต้อง

Student Intelligence Layer เป็นก้อนเดียวในมุมของผลิตภัณฑ์ ภายในก้อนนี้มี LLM สำหรับสนทนา ตัวจัดการ Learner Profile และ RAG สำหรับค้นข้อมูล ส่วนการตัดสินใจเชิงคะแนนแยกออกมาเพื่อให้ตรวจสอบได้

ลูกศรทึบคือข้อมูลที่ระบบส่งหากันระหว่างการใช้งาน ลูกศรประคือส่วนเสริมหรือ feedback จุดที่ควรย้ำคือ RAG ส่ง “หลักฐาน” ให้ Recommendation Engine ไม่ได้เป็นผู้เลือกเส้นทางแทนนักเรียน

Component Responsibilities

แต่ละส่วนรับผิดชอบอะไร และส่งอะไรต่อ

การกำหนด input และ output ให้ชัดตั้งแต่แรก จะช่วยให้ทีมพัฒนาแยกกันได้ และลดปัญหาที่ LLM รับทุกหน้าที่จนทดสอบไม่ได้

1

Student / Web App

หน้าจอสนทนา แสดง Profile ให้เด็กตรวจ แสดงเส้นทางหลายแบบ เปิดดูเหตุผลและแหล่งอ้างอิง รวมถึงรับ feedback หรือคำขอลบข้อมูล
ส่งต่อข้อความตอบกลับ การยืนยัน Profile ข้อจำกัด และ feedback
2

Student Intelligence Layer

ศูนย์กลางของประสบการณ์ผู้ใช้ คุยกับนักเรียน สร้างและอัปเดต Learner Profile ตรวจข้อมูลที่ยังขาด แล้วเรียก RAG เพื่อหาหลักฐานที่เกี่ยวข้อง
ส่งต่อProfile + Constraints + Evidence + Confidence + Missing information
3

Base LLM

เข้าใจภาษาธรรมชาติ ถามต่อเมื่อข้อมูลไม่พอ สกัดบทสนทนาเป็น JSON และเรียบเรียงคำอธิบายจากข้อมูลที่ระบบเตรียมให้
ไม่ควรทำจำข้อมูลรับสมัครล่าสุด สร้างหลักฐาน คิดคะแนน หรือฟันธงอาชีพ
4

Learner Profile DB

เก็บความสนใจ หลักฐานทักษะ บริบทงานที่ชอบ ข้อจำกัด เป้าหมาย ระดับความมั่นใจ และสถานะการยืนยันของผู้เรียน แยกข้อมูลระบุตัวบุคคลออกจาก Profile เท่าที่ทำได้
ส่งต่อProfile ที่มี version และเฉพาะ field ที่จำเป็นต่อคำขอนั้น
5

Knowledge Base + RAG

เก็บข้อความที่แบ่งเป็น claim หรือ chunk พร้อม Vector และ metadata เมื่อมีคำถาม ระบบจะค้นทั้งความหมายและคำตรง แล้วกรองปี จังหวัด ระดับวุฒิ ภาษา และสถานะข้อมูล
ส่งต่อEvidence ID, เนื้อหาที่พบ, แหล่งที่มา, วันที่ และ retrieval score
6

Recommendation & Scoring

จับคู่ Profile กับเส้นทางที่ RAG พบ คำนวณคะแนนหลายมิติ ตรวจเงื่อนไขบังคับ และสร้างอันดับพร้อมองค์ประกอบคะแนน
ส่งต่อหลายเส้นทาง + score breakdown + reasons + gaps + evidence IDs
7

Response & Safety

ให้ LLM เรียบเรียงผล ตรวจว่าข้อความสำคัญมีหลักฐาน ไม่ใช้ภาษาฟันธง ไม่ตีตราตามเพศ ฐานะ หรือพื้นที่ และยอมรับเมื่อข้อมูลยังไม่พอ
ส่งต่อคำตอบหลายทางเลือก พร้อมเหตุผล ข้อจำกัด และ citation ที่เปิดดูได้
8

LoRA Adapter

ส่วนเสริมสำหรับปรับรูปแบบการสนทนา การสกัด schema หรือการอธิบายตาม rubric เมื่อทีมมีตัวอย่างที่ผู้เชี่ยวชาญตรวจแล้วและมี baseline ให้เทียบ
สถานะ MVPยังไม่จำเป็น เริ่มจาก prompt + structured output + evaluation ก่อน

Text → Vector → Retrieval

ข้อมูลกลายเป็น Vector ได้อย่างไร

Vector Database ไม่ได้แปลงข้อความให้เรา ตัวที่ทำหน้าที่นั้นคือ Embedding Model ส่วน Vector Database มีหน้าที่เก็บ Vector และค้นชิ้นข้อความที่ความหมายใกล้กับคำถาม

STEP 01

เก็บไฟล์ต้นฉบับ

เก็บไฟล์แบบไม่แก้ไข พร้อม URL วันที่ดึง checksum และเงื่อนไขการใช้งาน

STEP 02

อ่านข้อความ

ใช้ parser ตามชนิดไฟล์ ถ้าเป็น PDF สแกนจึงค่อยใช้ OCR และต้องตรวจลำดับการอ่าน

STEP 03

จัดโครงสร้าง

แยกชื่อหลักสูตร วิชาที่เรียน อาชีพปลายทาง ค่าใช้จ่าย และเกณฑ์สมัครออกจากกัน

STEP 04

แบ่ง Chunk

ใช้หัวข้อและความหมายเป็นหลัก ไม่ตัดกฎรับสมัครครึ่งประโยคหรือรวมหลายปีในก้อนเดียว

STEP 05

ตรวจแหล่ง

กำหนด verified, conditional หรือ unverified และไม่นำ unverified เข้า production index

STEP 06

สร้าง Embedding

ใช้ Embedding Model เดียวกันกับทั้ง chunk และคำค้น เพื่อเปรียบเทียบความใกล้ทางความหมาย

STEP 07

เก็บ Vector

เก็บ Vector คู่กับข้อความ Evidence ID ปี จังหวัด ระดับวุฒิ และวันหมดอายุ

STEP 08

ทดสอบ Retrieval

สร้างคำถามไทยที่เหมือนภาษานักเรียนจริง แล้ววัดว่า source ที่ควรพบติด Top-K หรือไม่

ค่าตั้งต้นสำหรับทดลอง

  • Chunk ราว 300–600 tokens และ overlap 50–100 tokens
  • ข้อมูลกฎให้แบ่งตามหนึ่งเงื่อนไขหรือหนึ่ง claim
  • ดึง candidate ราว 15–20 ชิ้น แล้วเหลือหลักฐาน 5–8 ชิ้นหลัง rerank
  • ทดสอบ threshold จากข้อมูลจริง ไม่ยึดค่าตัวอย่างเป็นค่าถาวร

สิ่งที่ห้ามหายระหว่างแปลงข้อมูล

  • ชื่อเอกสาร ผู้เผยแพร่ URL และเลขหน้า
  • ปีการศึกษา รอบรับสมัคร และวันหมดอายุ
  • ขอบเขตของ claim เช่น จังหวัด ระดับวุฒิ หรือกลุ่มตัวอย่าง
  • สถานะ verified/conditional/unverified และผู้ตรวจ

Recommended MVP Stack

โปรแกรมที่แนะนำสำหรับเวอร์ชันแรก

ชุดนี้เน้นให้ทีมทำเดโมได้เร็ว แต่ยังต่อยอดเป็น production ได้ โปรแกรมทุกตัวเปลี่ยนภายหลังได้ ตราบใดที่สัญญาข้อมูลระหว่างแต่ละส่วนยังเหมือนเดิม

ส่วนของระบบ ตัวเลือกหลัก หน้าที่ สถานะ
Frontend Next.js หน้าแชต Profile editor ผลลัพธ์ และแหล่งอ้างอิง ทำตอนนี้
Backend API Python + FastAPI ควบคุม session, profile, RAG, scoring และ model call ทำตอนนี้
Document parsing Unstructured + PyMuPDF อ่านข้อความจาก PDF, Word, HTML และส่ง OCR เมื่อจำเป็น ทำตอนนี้
RAG orchestration LlamaIndex หรือ Python ตรง ๆ จัด ingestion, chunking, retrieval และประกอบ context เลือกอย่างใดอย่างหนึ่ง
Embedding BGE-M3 + Sentence Transformers แปลงข้อความไทย/อังกฤษเป็น Vector และรองรับการค้นแบบ multilingual ทดลองก่อน
Vector Database Qdrant เก็บ Dense/Sparse Vector, payload และค้นแบบ hybrid ทำตอนนี้
Relational Database PostgreSQL เก็บ Learner Profile หลักสูตรเชิงโครงสร้าง กฎ และผลคะแนน ทำตอนนี้
Raw file storage S3-compatible / MinIO เก็บไฟล์ต้นฉบับแบบ immutable พร้อม checksum ทำตอนนี้
Base LLM Model API ที่รองรับ structured output สนทนา สกัด Profile และเขียนคำอธิบายจาก evidence ใช้ API ก่อน
Deployment Docker Compose → managed containers รันบริการในเครื่องและย้ายขึ้น cloud โดยไม่เปลี่ยนสถาปัตยกรรมหลัก เริ่มง่ายก่อน
LoRA / Reranker / Graph เพิ่มหลังวัด baseline แก้ปัญหาเฉพาะที่พิสูจน์แล้วว่า prompt หรือ retrieval ปัจจุบันยังไม่พอ ทำภายหลัง
ถ้าต้องการลดจำนวนระบบในเดโม: ใช้ PostgreSQL + pgvector แทน Qdrant ได้ แต่หากทีมต้องการ Dense + Sparse + Hybrid Search ตั้งแต่แรก Qdrant จะจัดการส่วน retrieval ได้ตรงกว่า

Data Placement

อะไรควรเก็บเป็น Vector และอะไรไม่ควร

ข้อมูลที่ต้องค้นจาก “ความหมาย” เหมาะกับ Vector Database ส่วนข้อมูลที่ต้องกรอง เปรียบเทียบ คำนวณ หรือควบคุม version เหมาะกับฐานข้อมูลเชิงโครงสร้าง

ข้อมูล ตำแหน่งหลัก เหตุผล ตัวอย่าง Metadata สำคัญ
คำอธิบายอาชีพและงานที่ทำจริง Vector DB นักเรียนใช้คำไม่เหมือนชื่ออาชีพทางการ แต่ความหมายใกล้กัน occupation_id, source, version, locale
คำอธิบายหลักสูตรและผลลัพธ์การเรียนรู้ Vector DB ต้องค้นจากความสนใจและทักษะที่เล่าเป็นภาษาธรรมชาติ program_id, institution, level, province
เกณฑ์รับสมัครที่เป็นข้อความ Vector DB + PostgreSQL ค้นเนื้อหาใน Vector แต่ใช้ field โครงสร้างตรวจเงื่อนไขและปี cycle, round, valid_until, status
ค่าเทอม คะแนนขั้นต่ำ จังหวัด PostgreSQL ต้องกรองและเปรียบเทียบด้วยค่าที่แน่นอน currency, academic_year, unit
Learner Profile และ consent PostgreSQL แยก schema/สิทธิ์ ต้องแก้ไข ลบ ทำ version และควบคุมสิทธิ์ได้ profile_version, confirmed_at, retention
PDF และไฟล์ต้นฉบับ Object Storage เป็นหลักฐานต้นทาง เก็บแบบ immutable และตรวจ checksum ได้ checksum, retrieved_at, license

Runtime Data Flow

ตอนนักเรียนคุยหนึ่งรอบ ข้อมูลไหลอย่างไร

รอบสนทนาไม่ควรจบที่การส่งข้อความเข้าโมเดลแล้วรอคำตอบ ระบบต้องผ่าน Profile, Retrieval, Scoring และ Safety ตามลำดับ

TURN 01

รับข้อความ

Backend รับข้อความและ session โดยไม่ส่งข้อมูลระบุตัวตนเกินจำเป็นไปยังโมเดล

TURN 02

สกัด Profile

LLM คืน structured output ว่าพบความสนใจ ทักษะ ข้อจำกัด หรือข้อมูลที่ยังขาดอะไร

TURN 03

ให้เด็กยืนยัน

ข้อมูลที่เป็นการตีความต้องถูกแสดงให้แก้ไขได้ ไม่เก็บเป็นข้อเท็จจริงทันที

TURN 04

สร้างคำค้น

ระบบเลือก index และ metadata filter จาก Profile ไม่ใช่ส่ง Profile ทั้งก้อนไปค้นแบบไร้ขอบเขต

TURN 05

ค้น Evidence

RAG คืนหลักสูตร อาชีพ และกฎที่เกี่ยวข้อง พร้อม source, date, status และ score

TURN 06

คำนวณคะแนน

Recommendation Engine ให้คะแนน candidate และตัดตัวเลือกที่ผิดเงื่อนไขบังคับ

TURN 07

เรียบเรียงคำตอบ

LLM รับเฉพาะ Profile ที่จำเป็น ผลคะแนน และ evidence ที่ผ่านการเลือกแล้ว

TURN 08

ตรวจและเรียนรู้

Safety ตรวจ citation และภาษา จากนั้น feedback ของเด็กย้อนกลับไปอัปเดต Profile

// ข้อมูลที่ Student Intelligence Layer ส่งให้ Recommendation Engine { "profile_version": "student_123:v4", "interests": ["คอมพิวเตอร์", "การแก้ปัญหา"], "skill_evidence": [{"skill": "คิดเป็นระบบ", "confidence": 0.72}], "constraints": {"province": ["กรุงเทพมหานคร"], "budget_per_year": 80000}, "evidence_ids": ["program_software_001", "occupation_dev_003"], "missing_information": ["พื้นฐานคณิตศาสตร์"] }

Safety & Data Protection

เพราะผู้ใช้เป็นนักเรียน ความปลอดภัยต้องอยู่ในโครงสร้าง

Safety ไม่ใช่ prompt ปิดท้ายอย่างเดียว แต่เริ่มตั้งแต่เก็บข้อมูลให้น้อย แยกสิทธิ์ และออกแบบให้เด็กแก้หรือโต้แย้งคำแนะนำได้

Data minimizationเก็บเฉพาะข้อมูลที่จำเป็นต่อการแนะแนว และไม่ถามข้อมูลอ่อนไหวโดยไม่มีเหตุผล
Identity separationแยกข้อมูลระบุตัวบุคคลออกจาก Learner Profile และใช้รหัสอ้างอิงแทนเมื่อเรียกโมเดล
Consent & controlกำหนด consent/assent ตามอายุ พร้อมช่องทาง export แก้ไข และลบข้อมูล
No implicit trainingไม่นำบทสนทนาหรือ Profile ไปฝึกโมเดลโดยอัตโนมัติ ต้องมีวัตถุประสงค์และความยินยอมแยก
Evidence-first outputข้อเสนอสำคัญต้องย้อนกลับถึงหลักฐาน และระบบต้องปฏิเสธการฟันธงเมื่อข้อมูลไม่พอ
Human reviewมีช่องทางให้ครูแนะแนวหรือผู้เชี่ยวชาญทบทวน โดยเฉพาะเคสเปราะบางหรือวิชาชีพควบคุม

MVP Build Order

ลำดับสร้างที่ช่วยลดความเสี่ยง

อย่าเริ่มจาก LoRA หรือโมเดลใหญ่ที่สุด ให้เริ่มจากข้อมูลที่ตรวจสอบได้ แล้วค่อยพิสูจน์ว่า retrieval และ recommendation มีประโยชน์จริง

Phase 1

Data foundation

ล็อก schema สำหรับ learner, occupation, program, pathway edge และ source evidence สร้าง source registry กับ quarantine สำหรับข้อมูลที่ยังตรวจไม่ได้

ผ่านเมื่อทุก recommendation edge มี source, status และวันที่ตรวจ
Phase 2

Guided discovery

ทำบทสนทนาที่ช่วยเด็กเล่าเหตุการณ์จริง สกัด Profile แบบ structured และให้เด็กแก้ไขก่อนนำไปใช้

ผ่านเมื่อเด็กเห็นและแก้ Profile ได้ ระบบแยก “สิ่งที่รู้” กับ “สิ่งที่คาด” ได้
Phase 3

RAG + explainable scoring

นำข้อมูล verified เข้า index สร้าง metadata filters ให้คะแนนห้ามิติ และส่งอย่างน้อยสามเส้นทางพร้อมเหตุผลและ citation

ผ่านเมื่อทุกคำแนะนำย้อนกลับถึง Profile และ Evidence ID ได้
Phase 4

Evaluation & trial

ทดสอบ retrieval, mapping, recommendation, safety และ usefulness กับนักเรียนหลายบริบท รวมถึงเคสที่ระบบควรตอบว่ายังสรุปไม่ได้

ผ่านเมื่อพบว่าเด็กเข้าใจเหตุผล เห็นทางเลือกเพิ่ม และรู้ว่าจะทดลองอะไรต่อ
Phase 5

Optimization

ค่อยพิจารณา reranker, LoRA, Knowledge Graph, caching, autoscaling หรือโมเดลเฉพาะทางจากปัญหาที่วัดได้แล้ว

ผ่านเมื่อของที่เพิ่มทำให้ metric ดีขึ้นเหนือ baseline อย่างชัดเจน

Common Failure Modes

หกอย่างที่ทีมควรหลีกเลี่ยงตั้งแต่ต้น

1–3: ปัญหาด้านข้อมูล

  • ใส่ทุกอย่างลง Vector DB จนกรองค่าเทอม ปี และเงื่อนไขที่แน่นอนไม่ได้
  • รวมหลายหัวข้อหรือหลายปีไว้ใน Chunk เดียว ทำให้ citation พาไปผิด claim
  • นำข้อมูล unverified หรือหมดอายุเข้า production retrieval

4–6: ปัญหาด้านโมเดล

  • ปล่อยให้ LLM คิดคะแนนหรือสร้างเหตุผลที่ไม่มีอยู่ใน evidence
  • ใช้ LoRA จำหลักสูตรและเกณฑ์รับสมัครที่เปลี่ยนทุกปี
  • ให้ผลลัพธ์เป็นคำตอบเดียวจนเด็กเข้าใจว่า AI กำลังตัดสินชีวิตแทน

ระบบที่ดีไม่ได้ตอบเร็วที่สุด แต่ช่วยให้เด็กตัดสินใจจากข้อมูลที่เห็นและโต้แย้งได้

เป้าหมายของ MVP จึงไม่ใช่ทำให้ AI ดูฉลาดที่สุด แต่คือพิสูจน์ว่า Profile ถูกสร้างอย่างไม่ชี้นำ RAG ค้นหลักฐานได้ตรง คะแนนอธิบายได้ และเด็กมองเห็นก้าวทดลองถัดไปของตัวเอง

Build evidence first. Optimize the model later.
